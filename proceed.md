1. **OTP Expiry Source:**

     `const expiryMinutes = parseInt(process.env.OTP_EXPIRY_MINUTES || '5', 10);`
   - Advocate Password Reset OTPs: generated in `src/services/advocateReset.service.js:44` with a 10-minute validity (`otpExpiresAt = new Date(Date.now() + 10 * 60 * 1000)`).
   - In `email.service.js`, `options.expiryMinutes` will default to `parseInt(process.env.OTP_EXPIRY_MINUTES || '5', 10)`.

2. **Frontend URLs:**
   - Evaluated from existing config: `process.env.WEB_CLIENT_URL || process.env.CLIENT_URL || 'http://localhost:5173'`
   - Client bookings target: `${clientUrl}/my-bookings`
   - Advocate appointments target: `${clientUrl}/advocate/appointments`

3. **Amounts & Date/Time Formatting:**
   - Amounts: Always read from stored snapshot in `AdvocateBooking` (`feePaise`, `gstPaise`, `platformFeePaise`, `totalPaise`). Converted to ₹ with 2 decimals using Indian number formatting: `₹${(paise / 100).toLocaleString('en-IN', { minimumFractionDigits: 2, maximumFractionDigits: 2 })}`.

## 4. Service & Cron Implementation (`email.service.js`)

1. **Singleton Transporter:**
   - Module-level lazy initialized nodemailer transporter.
   - From address: `"VakeelSetu" <${process.env.EMAIL_USER}>`.
2. **Internal Helper `sendBrandedMail({ to, subject, html, text, attachments })`:**
   - Automatically attaches logo CID attachment if file exists.
   - Sanitized logging: `type`, masked recipient (`ra***@gmail.com`), `messageId`, `success: true`. Never logs OTPs or full HTML in any environment.
   - Dev fallback: if `EMAIL_USER` is missing or placeholder (`your-email@gmail.com`):
     - If `NODE_ENV === 'production'`: **throws error immediately; never logs OTPs**.
     - If non-production: prints `[DEV EMAIL SERVICE] OTP to ...` (or masked log).
3. **`sendEmailOtp(to, otp, options = {})`:**
   - Preserves original `(to, otp)` signature while supporting `options = { recipientName, purpose, expiryMinutes }`.
   - Defaults `expiryMinutes` to `process.env.OTP_EXPIRY_MINUTES || '5'`.
4. **`sendAdvocateBookingConfirmationEmails(bookingId)`:**
   - Fetches `AdvocateBooking` with `user`, `advocate`, and `payment.attempts`.
   - **Atomic Claiming Pattern (Independently for User and Advocate):**
     ```js
     // User email
     if (!booking.userEmail?.trim()) {
       console.info(`[Email Service] Skipping user booking confirmation email for booking ${bookingId}: no user email on record.`);
     } else {
       const claim = await prisma.advocateBooking.updateMany({
         where: { id: bookingId, userConfirmationEmailSentAt: null },
         data: { userConfirmationEmailSentAt: new Date() }
       });
       if (claim.count > 0) {
         try {
           await sendBrandedMail({ ...userMailOptions });
         } catch (err) {
           await prisma.advocateBooking.update({
             where: { id: bookingId },
             data: { userConfirmationEmailSentAt: null }
           }).catch(() => {});
           console.error(`[Email Service] Failed sending user booking confirmation for ${bookingId}:`, err.message);
         }
       }
     }

     // Advocate email
     if (!booking.advocate?.email?.trim()) {
       console.info(`[Email Service] Skipping advocate booking confirmation email for booking ${bookingId}: no advocate email on record.`);
     } else {
       const claim = await prisma.advocateBooking.updateMany({
         where: { id: bookingId, advocateConfirmationEmailSentAt: null },
         data: { advocateConfirmationEmailSentAt: new Date() }
       });
       if (claim.count > 0) {
         try {
           await sendBrandedMail({ ...advocateMailOptions });
         } catch (err) {
           await prisma.advocateBooking.update({
             where: { id: bookingId },
             data: { advocateConfirmationEmailSentAt: null }
           }).catch(() => {});
           console.error(`[Email Service] Failed sending advocate appointment email for ${bookingId}:`, err.message);
         }
       }
     }
     ```
   - **Never throws** out of `sendAdvocateBookingConfirmationEmails`, ensuring booking and payment flows are never disrupted.
5. **Execution Trigger in `payment.service.js`:**
   - Called right after transaction commits when an `AdvocateBooking` transitions to `CONFIRMED`.
   - Wrapped with an 8-second timeout (`withTimeout(sendAdvocateBookingConfirmationEmails(booking.id), 8000)`).
   - If timeout or error occurs, caught gracefully and logged; cron retries later.
6. **Reconciliation Cron in `paymentCron.controller.js`:**
   - Reconcile cron (`/api/internal/cron/payments-reconcile`) queries bookings created in the last 48 hours where status is `CONFIRMED` or `COMPLETED` and either timestamp is `null`:
     ```js
     const fortyEightHoursAgo = new Date(Date.now() - 48 * 60 * 60 * 1000);
     const pendingBookings = await prisma.advocateBooking.findMany({
       where: {
         createdAt: { gte: fortyEightHoursAgo },
         status: { in: ['CONFIRMED', 'COMPLETED'] },
         OR: [
           { userConfirmationEmailSentAt: null },
           { advocateConfirmationEmailSentAt: null }
         ]
       },
       select: { id: true },
       take: 25
     });
     for (const b of pendingBookings) {
       await sendAdvocateBookingConfirmationEmails(b.id).catch(() => {});
     }
     ```

## 7. Risks & Mitigations

1. **Risk:** Slow or unresponsive SMTP provider causes HTTP timeout during Razorpay payment verification.  
   **Mitigation:** `sendAdvocateBookingConfirmationEmails` is wrapped in an explicit 8-second timeout (`withTimeout`). Failure or timeout never fails the payment or HTTP response. Reconcile cron automatically retries.
2. **Risk:** Concurrency race between Razorpay webhook and frontend verify causing duplicate emails.  
   **Mitigation:** Atomic database row claiming using `prisma.advocateBooking.updateMany` with `where: { id, ...EmailSentAt: null }`. Only the single request updating the row receives a count of 1 and triggers email delivery.
3. **Risk:** Missing logo image crashing the serverless function.  
   **Mitigation:** `fs.existsSync` check dynamically falls back to unicode scales symbol `&#9878;` with no CID attachment.
4. **Risk:** Accidental real emails sent during test runs or dev environment.  
   **Mitigation:** Stubbed transporter in tests. Dev fallback strictly guarded by `process.env.NODE_ENV !== 'production'`.
5. **Risk:** Phone-only user without email causing endless cron retries.  
   **Mitigation:** 48-hour cutoff window on `createdAt` in cron queries ensures stale records without emails stop being evaluated after 48 hours.
